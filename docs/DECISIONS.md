- **Accepted:** decided and ready to build on.

## Platform & tooling

### D-001: pnpm workspace modular monolith, no Turborepo (yet)

**Decision:** Four packages as briefed: `apps/web`, `apps/worker`, `packages/db` and `packages/shared`. Root scripts use `pnpm -r`/`--filter`. `packageManager` is pinned in the root `package.json`, and pnpm itself is installed through corepack.
**Why:** Four packages don't need a task-graph cache. There's one fewer tool to learn.
**Alternatives:** Turborepo, which adds remote caching we don't need. Nx, which is heavy.
**Follow-up:** Add Turborepo if CI builds exceed about 5 minutes.

### D-002: Node.js 24 LTS in every container

**Decision:** Pin `node:24-*` images and `"engines": { "node": ">=24 <25" }`. Local development may use a newer Node; CI uses 24.
**Why:** pg-boss 12 requires Node ≥ 22.12, and Prisma 7 requires ≥ 20.19. Node 24 is the current LTS line.
**Alternatives:** Node 22, which is older with a shorter runway. Node 26, which is not LTS yet.

### D-003: TypeScript 6.0.x, not 7 (yet)

**Decision:** Use `typescript@~6.0` workspace-wide with `strict`, `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.
**Why:** TypeScript 7 (the native port) is out, and Next 16.3 can use it for `next build` type checking. However, `typescript-eslint@8.71` declares `typescript >=4.8.4 <6.1.0`, and type-aware linting is worth more to us than faster checks.
**Alternatives:** TypeScript 7 plus Biome for linting. Biome has fewer type-aware rules, and we'd lose `eslint-config-next`.
**Follow-up:** Switch when typescript-eslint supports TypeScript 7. Next's `useTypeScriptCli` option makes the build side a one-line change.

### D-004: ESLint 10 flat config + typescript-eslint + Prettier

_Amended 2026-09-29: `apps/web` stays on **ESLint 9**. `eslint-plugin-react` (pulled in by `eslint-config-next` 16.3) crashes on ESLint 10 (`Components.componentRule`). The other packages use ESLint 10 through the root `eslint.config.js`. Move web to 10 once `eslint-config-next` supports it._
**Decision:** `eslint.config.ts` at the root with `eslint-config-next@16.3`, `typescript-eslint` `strictTypeChecked`, and custom rules:

- `no-restricted-imports` bans importing `@dopl/db` (Prisma) from React components and client code. Data access only goes through `apps/web/src/server/**`.
- `no-explicit-any` is an error.
- A JSX literal-string rule forces strings through next-intl.

Formatting is Prettier with `prettier-plugin-tailwindcss`.
**Why:** `next lint` was removed in Next 16; ESLint's CLI is used directly.

## Next.js

### D-005: Cache Components + Partial Prefetching on from day one

**Decision:**

```ts
// apps/web/next.config.ts
const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
  reactCompiler: true,
  typedRoutes: true,
};
```

**Why:** The brief's first principle is "Fast". Instant Navigations is exactly that: every link prefetches a reusable App Shell, and dynamic parts stream into `<Suspense>` fallbacks that we design as skeletons. Next says this becomes the default in the next major, so adopting it on a greenfield app costs almost nothing now and a migration later. The dev-time validation also flags any navigation that would block, which enforces "no full-page spinners" for free.
**How it maps onto Dopl:**

- The **static shell** is the canvas, the sidebar frame, the inset panel and skeletons for the page header, toolbar and list.
- The **session-dependent** parts sit inside `<Suspense>` with skeletons. These are the sidebar's projects, the inbox badge and page data, which read `cookies()` through the auth helper. Per-user data that is fine to show slightly stale (the sidebar project list, the member directory) uses `'use cache: private'` with `cacheLife({ stale: 300 })`, so it lands in the App Shell. Realtime events then call `router.refresh()` or update the TanStack Query cache.
- Interactive views (list, board, table) hydrate into TanStack Query (D-009). After first paint, freshness comes from realtime, not from Next's cache.
- Public intake forms (`/f/[slug]`) use `'use cache'` tagged `form:<id>` and are revalidated with `updateTag` when the form is saved.

**Tests:** Critical navigations get `@next/playwright` `instant()` tests: sidebar to a project list, list to peek panel, and project to project.
**Alternatives:** Plain dynamic rendering with `loading.tsx` files. That's simpler to start, but it's the model Next is moving away from, and it's easy to miss one and ship a blocking navigation.
**Risk:** Partial Prefetching is new (16.3). If it misbehaves with authenticated routes, we can turn it off without code changes and keep Cache Components.

### D-006: React Compiler on (Babel), Rust compiler later

**Decision:** `reactCompiler: true`. We don't use the experimental `turbopackRustReactCompiler` yet.
**Why:** Automatic memoization matters for big lists and boards with inline editors.
**Caveat:** Table instances and virtualizers are mutable objects. If a TanStack Table or Virtual component misbehaves under the compiler, mark it with `"use no memo"` and note that in the component.

### D-007: `proxy.ts` does optimistic cookie checks only

**Decision:** `apps/web/src/proxy.ts` (Next 16 renamed `middleware.ts` to `proxy.ts`) only does two things:

- It redirects to `/sign-in` when no Better Auth session cookie is present. It uses `getSessionCookie()` and does no database access.
- It sets security headers.

All real authorization happens server-side in the policy module (see `docs/ARCHITECTURE.md` §7).
**Why:** Proxy runs on every request, including prefetches, so a database round-trip there would slow everything down. Better Auth's docs make the same recommendation.

### D-008: Server actions for UI mutations, route handlers for the rest

**Decision:**

- **Server actions** (`'use server'`, zod-validated, policy-checked) handle every mutation made from the authenticated UI.
- **Route handlers** handle:
  - `/api/auth/[...all]` (Better Auth)
  - `/api/realtime` (SSE)
  - `/api/mcp` (MCP)
  - `/api/public/**` (form submit, uploads, status-page replies; CORS-aware and rate-limited)
  - `/api/files/**` (signed download redirects)
  - `/embed.js`
  - health checks
    **Why:** Server actions give us typed calls and built-in origin checks. Public and embed endpoints need explicit CORS, caching and rate-limit control, and must not depend on a Next build id.

### D-009: RSC first load → TanStack Query, realtime-driven cache

**Decision:**

1. A Server Component fetches the first page of data through `server/queries/*`.
2. It passes that data to a client view via `<HydrationBoundary>`.
3. From then on, TanStack Query owns the data.
4. Mutations use `useMutation` with optimistic `onMutate`, rolling back on error.
5. Realtime events patch or invalidate query keys.

Query keys come from one factory in `@dopl/shared`, shared by the client and the realtime mapper.
**Why:** RSC gives us the fast first paint. TanStack Query gives us optimistic updates, refetch-on-focus and fine-grained cache edits that Server Components alone can't.
**Rule:** A view never _both_ `router.refresh()`es and patches Query for the same data. Each piece of data has exactly one owner.

## Data

### D-010: Prisma pinned to 7.x, ESM client, explicit pool settings

**Decision:**

- Pin `prisma@~7.10` and `@prisma/client@~7.10`. **npm's `latest` tag for `prisma` already points at `8.0.0-rc.17`**, so a bare `pnpm add prisma` or `npx prisma` would pull the v8 RC. The CLI also shows a banner urging you to upgrade to v8. Ignore it.
- The generator is `prisma-client` with `output = "../src/generated/prisma"` and `moduleFormat = "esm"`. Import the client from `@dopl/db`, which re-exports it. Never import from `@prisma/client`.
- `packages/db/prisma.config.ts` does `import "dotenv/config"` and holds the datasource URL.
- The driver adapter is `@prisma/adapter-pg` with explicit settings. Prisma 7's `pg` defaults are **no** connect or acquire timeout and a 10 s idle timeout:
  ```ts
  new PrismaPg({
    connectionString: env.DATABASE_URL,
    max: 10, // web; worker uses 5
    connectionTimeoutMillis: 5_000,
    idleTimeoutMillis: 30_000,
    statement_timeout: 30_000, // passed through to pg
    application_name: "dopl-web", // or dopl-worker
  });
  ```
- `prisma generate` and `prisma db seed` are explicit steps. In v7, `migrate dev` no longer runs them automatically.
  **Alternatives:** Drizzle, which wasn't chosen because the stack is fixed by the brief.

### D-011: UUIDv7 primary keys generated by Prisma — _Verified_

**Decision:** `id String @id @default(uuid(7)) @db.Uuid`. Better Auth is configured with `advanced.database.generateId: false` so its tables use the same defaults.
**Why:** Time-ordered ids give good B-tree locality and cursor pagination with `(createdAt, id)`. They're also safe to expose in URLs, and there are no integer ids to enumerate.
**Caveat:** The value is generated by the Prisma client, not the database. Raw SQL inserts must supply an id using the `uuidv7()` helper in `@dopl/shared`. (Postgres 18 has a native `uuidv7()`, but we target 17.)

### D-012: Table/column naming

**Decision:** Tables are snake_case plural via `@@map` (`work_items`, `users`). Columns keep Prisma's camelCase.
**Why:** Plural names avoid reserved words like `user`, and `psql` stays pleasant to use. Mapping every column would double the schema's size for little gain.
**Cost:** Raw SQL must quote columns (`"createdAt"`).

### D-013: Tenancy: `workspaceId` everywhere, app-layer policy (no RLS)

**Decision:** Every tenant row has `workspaceId`.

- _Root_ entities have a real FK to `Workspace`: Project, Contact, Mailbox, Channel, Note, View and so on.
- _Child_ rows carry it as a denormalized scalar. The domain layer copies it from the parent row it has already loaded and authorized, never from client input.
- Every query goes through `server/data/*` functions that take a `Ctx` (actor + workspace) and add the scope.

**Why:** There is one workspace today, but the model stays multi-tenant-ready at almost no cost.
**Alternatives:** Postgres row-level security. It's stronger, but it needs a per-request `SET app.workspace_id`, which doesn't fit well with pooled driver-adapter connections and doubles the policy surface. We'll revisit if Dopl ever hosts several organisations.

### D-014: Fractional-index string keys with `COLLATE "C"` — _Verified_

**Decision:** Manual ordering (board cards, list manual order, states, sidebar, form fields) uses `fractional-indexing` string keys in `sortKey` columns. A hand-written migration changes those columns to `COLLATE "C"`.
**Why:**

- Float sort orders (Plane's approach) run out of precision after about 50 inserts at the same spot and then need rebalancing.
- Fractional keys never do. But they compare correctly **only in byte order**. Under the default `en_US` collation, `"Zz" > "a0"`, and the library produces exactly such keys when you insert above the first item.
- The spike on Postgres 17.11 with Prisma 7.10 confirmed that Prisma ignores column collation when diffing, so there's no migration drift.

**Follow-up:** A CI test inserts keys produced by `generateKeyBetween(null, first)` and checks the database orders them correctly.

### D-015: Hand-written SQL migrations alongside Prisma's — _Verified_

**Decision:** Things Prisma can't express go in separate, hand-written migrations named `*_manual_*`:

- `COLLATE "C"`
- CHECK constraints ("exactly one owner FK")
- the append-only trigger on `audit_logs`
- the `search` schema

Developers let Prisma create its **own temporary shadow database**; there's no `shadowDatabaseUrl` in dev.
**Why:** The spike showed:

- `migrate dev` stays drift-free with all of the above.
- A _fixed_ shadow database keeps objects in non-`public` schemas between runs, and the next replay then fails with "relation already exists".

**Follow-up:** Manual migrations use `IF NOT EXISTS` where possible. CI runs `prisma migrate diff --from-migrations … --to-schema …` and fails on a non-empty diff.

### D-016: Search: `pg_trgm` first, full-text later

**Decision:** Use GIN `gin_trgm_ops` indexes, declared in Prisma, on:

- work item titles
- message and note text
- email subjects
- contact emails

The ⌘K search queries these with `ILIKE` and `similarity()`.
**Why:** Trigram search handles substrings, typos, identifiers (`INFRA-4`) and mixed Dutch/English text without a stemming configuration. It covers tens of thousands of rows easily.
**Later:** Weighted `tsvector` expression indexes, or semantic search (D-017), if relevance becomes a problem.

### D-017: Embeddings live in a `search` schema outside Prisma — _Verified_

**Decision:** `search.embeddings` (`vector(N)`, HNSW cosine index) is created by a manual migration and accessed with raw SQL from `packages/db/src/search`. It is _not_ in `schema.prisma`.
**Why:** Prisma 7 handles `Unsupported("vector(1024)")` columns without drift. (Issue prisma#28867, drift on an unsized `vector`, did not reproduce on 7.10.) However, Prisma can't express an **HNSW index**, and every `migrate dev` generated `DROP INDEX embeddings_embedding_hnsw`. Keeping the table in a schema Prisma doesn't manage made the diff empty.
**Open:** The vector dimension depends on the embedding model on your AI server (see Q-6). I assumed 1024 for now; changing it before Phase 5 is free.

### D-018: Intake = TRIAGE-state work item + IntakeItem; numbers on accept

**Decision:** Each submission creates a `WorkItem` in the project's hidden **TRIAGE** state group, plus an `IntakeItem` holding the status, source, contact and snooze. `WorkItem.sequence` stays `NULL` until the item is accepted, and triage shows "Intake #12" from its own per-project counter.
**Why:**

- Comments, attachments, activity and the status page work the same way before and after triage. There's one timeline and no copying data at accept time.
- Declined spam never uses up `INFRA-n` numbers.

**Alternatives:**

- A standalone intake entity that is copied into a work item on accept. That means two timelines and a lossy conversion.
- Plane's approach, which assigns sequence ids on submission.

### D-019: Rich text stored as Tiptap JSON + derived plain text

**Decision:** Store ProseMirror JSON (`Json`) plus a `…Text` column derived on the server when saving, used for search, previews, notifications and embeddings.

- Mentions are a `mention` node (`{ id, kind: user|agent }`).
- Work-item references are a custom `workItemRef` node (`{ id, identifier }`), created by typing `#`.
- Task items carry a stable `blockId` attribute (D-022).
- Server-side HTML, used in emails and the status page, comes from `@tiptap/static-renderer`.

**Why:** JSON is lossless and lets us walk the document reliably for mentions, references and to-dos. HTML would need re-parsing.
**Rule:** Content from the client is validated against an allowlist of node and mark types with zod before storing.

### D-020: Archive vs soft delete, 30-day purge

**Decision:**

- `archivedAt` is user-facing ("Archive"): the row is hidden from views and restorable any time.
- `deletedAt` is soft delete: an undo toast, a trash view, and a hard purge after **30 days** by a nightly worker job. The window is confirmable (Q-11).

Configuration entities (states, labels) are hard-deleted, with a reassignment step for states. Their names survive in the history because Activity rows keep snapshots in `meta`.

### D-021: Denormalized `stateGroup` and counters on WorkItem

**Decision:** `WorkItem.stateGroup`, `childCount`, `childDoneCount`, `commentCount` and `attachmentCount` are maintained in the same transaction as the change that affects them. A `pnpm db:recount` script can rebuild them.
**Why:** Group-by-state-group, "open vs done" filters, sub-item progress rings and list badges become index-only reads without joins. That matters for 10k-row tables and cross-project views.

### D-022: Note to-dos are a projection keyed by stable block ids

**Decision:** A note's content is the source of truth. On every save, the server walks the task items and upserts `NoteTodo` rows keyed by `(noteId, blockId)`. Toggling a to-do from "My to-dos" rewrites that one node in the note JSON (matched by `blockId`) and the projection in one transaction.
**Why:** It keeps Blinko-style inline checkboxes while making "all my open to-dos across notes" a simple indexed query. It also gives each line an id that can be turned into a work item.

## Realtime & jobs

### D-023: Realtime: transactional outbox + `pg_notify` + SSE

**Decision:** Every mutation inserts a `realtime_events` row (topic, type, small payload) **in the same transaction** and calls `SELECT pg_notify('dopl_realtime', <event id>)`. Postgres only delivers NOTIFY on commit, so rolled-back changes never broadcast.

Each web process holds **one** dedicated `LISTEN` connection, outside the Prisma pool, with reconnect and backoff. It fans events out to that process's SSE clients after an in-memory permission filter.

Clients use `EventSource('/api/realtime')`:

- They reconnect with `Last-Event-ID`.
- The server replays missed events from the table, which keeps 24 hours.
- If the gap is too large, the server sends `resync` and the client invalidates all queries.

Each browser shares one connection across tabs via `BroadcastChannel` leader election.
**Why:** No Redis (as briefed), exactly-once-per-commit semantics, replay for free, and NOTIFY's 8 KB payload limit stops mattering because we only send ids.
**Ephemeral signals** (typing indicators) use `pg_notify` directly with no row. Collision presence uses heartbeat rows in `presences` so late joiners see who is already there.

### D-024: pg-boss 12 in its own schema, separate worker

**Decision:**

- `apps/worker` runs pg-boss 12 with `schema: 'pgboss'`, a schema Prisma never sees.
- Web enqueues jobs by importing only the pg-boss _publisher_ (`send`), with no workers in the web process.
- Jobs are idempotent and use `singletonKey` where duplicates are possible, for example `gmail.sync:<mailboxId>`.
- Recurring work uses pg-boss `schedule()` with the workspace timezone. That includes watch renewal, snooze wake-ups, the daily review, analytics snapshots, purges and pruning.

**Why:** Postgres-backed with no Redis, as briefed. pg-boss 12 has cron schedules, retries with backoff, dead-letter queues and a singleton policy.

### D-025: Rate limiting in Postgres

**Decision:** Fixed-window counters in `rate_limit_counters`, using an upsert with `count + 1 RETURNING count`. Keys are:

- `ip:<sha256(ip+salt)>:<route>`
- `email:<hash>:<route>`

A nightly job prunes expired rows. Better Auth uses its own `auth_rate_limits` table (`rateLimit.storage: "database"`).
**Why:** It works across multiple web replicas with no extra infrastructure. At our traffic (an internal tool plus public forms), each check costs about one indexed write.

## Auth & security

### D-026: Auth: Better Auth (Google `hd` + guest magic links), contacts tokenized

_Partly superseded by D-050: accounts are invite-only for everyone, and more sign-in methods were added. The contact and agent parts still apply._
**Decision:**

- **Members** sign in with Google.
  - The Google provider sets `hd: "<your-domain>"`, and Better Auth rejects tokens without a matching `hd` claim.
  - A `databaseHooks.user.create.before` hook also checks the email domain against `Workspace.allowedEmailDomains`, as defense in depth.
  - The first sign-in auto-creates a MEMBER if `autoJoinDomainUsers` is set (Q-2). Otherwise an invite is required.
- **Guests** use the `magicLink` plugin with `disableSignUp: true`. A guest must be invited first; the invite creates the user row. `sendMagicLink` refuses addresses on the member domain, so those users must use Google.
- **Contacts** (public form submitters) get **no account**. The confirmation email carries a random token; only its SHA-256 is stored in `contact_access_tokens`. It is scoped to one submission, lasts 90 days, and is renewed each time it's used. `/s/<token>` swaps it for a short-lived, path-scoped signed cookie.
- **Agents** never sign in. They authenticate to MCP with bearer tokens (D-032).
- Sessions use `session.cookieCache` (5 minutes) to avoid a database lookup per request, with `nextCookies()` enabled for server actions.

**Why:** It matches the brief exactly and keeps untrusted outsiders completely separate from the user table.

### D-027: Web never holds Google or SSH credentials

**Decision:** The Google service-account key (domain-wide delegation) and the agent's SSH key are mounted **only in the worker container**. When the web process needs Gmail data (for example, an attachment on first open), it enqueues a job and waits for the result (LISTEN, with a timeout), then redirects to a signed object-storage URL.
**Why:** The web process is internet-facing because of public forms. A web compromise then can't read every mailbox or reach every server.

### D-028: Email HTML: sanitize at ingest + sandboxed iframe

**Decision:**

1. At ingest, the worker sanitizes HTML with DOMPurify on jsdom:
   - strips `script`, event handlers, `form`, `iframe`, `object`, `meta refresh` and `javascript:` URLs
   - rewrites remote `img`/`background` URLs to `data-dopl-src`
   - sets `hasRemoteImages`
2. The UI renders `bodyHtmlSanitized` in an `<iframe sandbox="allow-popups allow-popups-to-escape-sandbox" srcdoc=…>` with a CSP `<meta>` of `default-src 'none'; img-src data: cid:; style-src 'unsafe-inline'`. There is **no** `allow-scripts` and no `allow-same-origin`.
3. Links open in a new tab with `rel="noopener noreferrer"`.
4. "Load images" re-renders the email with images routed through `/api/files/image-proxy`, which hides the reader's IP and blocks tracking pixels.

`cid:` images and attachments are fetched lazily (D-027).
**Why:** Two independent layers, so one sanitizer bug isn't enough to break out.

### D-029: CSP without nonces initially

**Decision:** Send `Content-Security-Policy` with:

- `default-src 'self'`
- `script-src 'self' 'unsafe-inline'`
- `connect-src 'self'`
- `img-src 'self' data: blob:`
- `frame-ancestors 'none'`, except `/f/*`, which uses per-form allowed origins
- `object-src 'none'; base-uri 'self'; form-action 'self'`

**Why:** Nonce-based CSP forces every page to render dynamically, which cancels out D-005's static shells. Next inlines RSC bootstrap scripts, so `'unsafe-inline'` is needed without nonces or hashes.
**Follow-up:** In the Phase 1 hardening step, evaluate hash-based CSP (Next's SRI support) and adopt it if it works with Partial Prefetching.

## Integrations

### D-030: Hermes via its API-server **Runs API**

**Context:** Hermes offers three protocols:

- **ACP:** stdio, aimed at IDEs.
- **TUI-gateway JSON-RPC:** stdio or WebSocket, with approvals sent as server→client `approval` requests.
- **OpenAI-compatible API server:** HTTP + SSE.

The API server exposes `POST /v1/runs`, `GET /v1/runs/{id}/events` (SSE), `POST /v1/runs/{id}/approval`, `/stop`, `/steer` and `GET /v1/capabilities`. Runs emit `approval.request` events and wait in `waiting_for_approval` until resolved. Choices are `once | session | always | deny`.

**Decision:** The worker drives Hermes through the **Runs API**:

- `Authorization: Bearer $HERMES_API_KEY`
- `Idempotency-Key: <AgentRun.id>`, which Hermes stores durably, so a worker retry never starts a second run
- `X-Hermes-Session-Id: dopl:<workItemId|channelId>`, which keeps conversation continuity per work item or DM
- `X-Hermes-Session-Key: dopl:<agentUserId>:<scope>`

At startup, the worker checks `GET /v1/capabilities` for `run_approval_response` and `approval_events` and refuses to enable the agent without them.

Dopl only ever answers `once` or `deny`. **Never `session` or `always`**, because every infrastructure action is approved individually.

**Why not the TUI gateway?**

- It's built for interactive hosts attached to a live, process-local session.
- Over WebSocket, it needs a `client.capabilities` handshake, or else approvals are rejected immediately.
- Its approval requests are only held while a client is attached.

Dopl is a headless control plane running in a job worker. HTTP with bearer auth, durable idempotent runs and a status endpoint to recover after restarts fit that much better. Both protocols can surface approvals, but approvals Hermes raises itself are the _secondary_ path anyway (D-031).
**Why not ACP?** It's stdio-only and designed around IDEs.
**Abstraction:** Everything goes through the `AgentRuntime` interface (`docs/ARCHITECTURE.md` §8), so swapping runtimes means one new adapter.

### D-031: Dopl's `infra_exec` MCP tool is the only way to touch infrastructure

**Context:** Hermes's own approval layer (`approvals.mode: manual|smart|off`) only asks about commands its _dangerous-pattern detector_ flags. A plain `docker run -p 8081:80 …` or `docker compose up -d` would not be flagged. The brief requires approval for **anything** that changes infrastructure state, with only an allowlist of read-only commands exempt.

**Decision:**

- Hermes is configured with its **terminal/code-execution toolsets disabled**, or at most a no-network sandbox for scratch work. Hermes has **no SSH key**.
- The only route to our servers is Dopl's MCP tool `infra_exec(run_token, host, command, reason)`. Dopl makes the decision:
  1. **Deny:** the host is not on the allowlist or not enabled, a DENY rule matches, the agent is paused, or the run was cancelled.
  2. **Run immediately:** only if the run is _not_ tainted, the host doesn't have `alwaysRequireApproval`, and the full normalized command matches an ALLOW_READONLY rule. Commands with compound operators (`;`, `&&`, `|`, `` ` ``, `$(`) or redirections never match an allowlist rule, unless the rule was written explicitly for that pattern.
  3. **Otherwise, ask a human:** Dopl creates an `AgentApproval` and notifies approvers in the Inbox with a realtime badge. The tool call waits (see D-032). Approve runs it; deny returns `DENIED by <name>: <note>` to the agent.
- Execution happens in the **worker**:
  - `ssh2` connects to Warpgate as `dopl-agent:<warpgateTarget>` with a dedicated, least-privilege key, so Warpgate records the session.
  - A hard timeout applies.
  - Output streams into `AgentRunStep` and the realtime channel. The head is stored in the database; the full log goes to object storage.
- Hermes-raised `approval.request` events (for any Hermes tool still enabled) are mirrored into the same `AgentApproval` UI as `RUNTIME_TOOL` and resolved via `/v1/runs/{id}/approval`.

**Why:** One enforcement point, fully under our control and audit, and the same whichever runtime is behind `AgentRuntime`. SSH keys never leave the worker.

### D-032: Dopl MCP server: Streamable HTTP, agent token + per-run token

**Decision:**

- `/api/mcp` is a Next route handler using `@modelcontextprotocol/sdk` 1.x with the **Streamable HTTP** transport. Hermes supports remote HTTP MCP servers with custom headers and a per-server `timeout`.
- **Auth:** `Authorization: Bearer <ApiToken>` (kind MCP, hashed, scoped, and optionally limited to certain projects), configured in Hermes's `mcp_servers.dopl.headers`.
- **Run correlation:** Hermes's MCP connections are static per server, so every Dopl tool takes a required `run_token` argument. This is a random, per-run capability token that Dopl puts in the run's instructions; only its hash is stored in `AgentRun.runTokenHash`. Dopl resolves the token to the run, and from there gets the scope, the taint state and the audit linkage.
  - A call without a valid token for a RUNNING run of _this_ agent is refused.
  - The token is useless outside Dopl's MCP endpoint and expires when the run ends. It is not an infrastructure secret.
- **Long waits:**
  - `infra_exec` blocks for up to 10 minutes and sends MCP progress notifications, so the connection stays alive. Hermes's `timeout` for the Dopl server is set to 900 s.
  - If a human hasn't decided by then, the tool returns `{ status: "pending_approval", approval_id }`.
  - The agent is told to call `infra_wait(run_token, approval_id)`, which also blocks for up to 10 minutes.
  - Approvals expire after `AgentProfile.approvalTimeoutSec` (default 1 hour).
- **Tool set (v1):**
  - `search_work_items`, `get_work_item`, `create_work_item`, `update_work_item`, `add_comment`
  - `list_assigned_threads`, `get_email_thread`
  - `list_hosts`, `infra_exec`, `infra_wait`

  Every write is recorded as an `Activity` with `actorType = AGENT` and the `agentRunId`.
  **Open:** Confirm reachability. Hermes must reach `https://<dopl>/api/mcp`, and the worker must reach Hermes's port 8642 (Q-7).

### D-033: Taint tracking for the prompt-injection boundary

**Decision:** Content has provenance:

- `WorkItem.untrusted` is set for `origin ∈ {INTAKE_FORM, INTAKE_GUEST, EMAIL}` or when a contact authored the description.
- Email threads are always untrusted.
- Contact and guest comments are untrusted.

Untrusted content is **never** sent to the agent automatically:

- No auto-triggers on intake or email.
- Assigning the agent to an untrusted item asks the assigner to confirm.

A run is tainted (`AgentRun.untrusted = true`, with `untrustedReasons`):

- **at start**, if its context includes untrusted content, or
- **during the run**, the moment an MCP read returns untrusted content (`get_email_thread`, or `get_work_item` on an untrusted item).

In a tainted run, **every** `infra_exec` needs approval (the allowlist is ignored), and every MCP write becomes an `MCP_WRITE` approval. The UI shows an "Untrusted input" banner on the run and its approvals.

An admin can clear `WorkItem.untrusted` after reviewing the content ("Mark as reviewed"). This is audit-logged.
**Why:** Flagging only at start would miss the classic attack, where the agent reads a hostile email halfway through a run. Taint-on-read closes that gap.

### D-034: One concurrent run per agent to start

**Decision:** `AgentProfile.maxConcurrentRuns = 1`. Extra runs queue.
**Why:** It makes run correlation (D-032) unambiguous, keeps load on the self-hosted 27B model predictable, and keeps the approval queue easy to follow. We'll raise it once the rest of the flow is proven.

### D-035: Gmail: DWD service account, Pub/Sub **pull**, `format=full`

**Decision:**

- **Credentials and scopes:**
  - Auth is a Google Cloud service account with domain-wide delegation. The worker acts as each connected mailbox's user (JWT `subject`).
  - Scopes are `gmail.readonly` and `gmail.modify`, plus `gmail.send` when replying is built.
  - Only mailboxes listed in `mailboxes` are ever touched.
- **Push:**
  - `users.watch({ topicName, labelIds: [...], labelFilterBehavior })` publishes to a Pub/Sub topic. `gmail-api-push@system.gserviceaccount.com` needs the Publisher role on it.
  - The worker consumes it with a **streaming pull** subscription through `@google-cloud/pubsub`, so there's no public webhook.
  - Notifications only carry `{emailAddress, historyId}`. They're used purely as a "sync now" trigger, deduplicated by `singletonKey`.
- **Incremental sync:**
  - `history.list(startHistoryId)`, with types `messageAdded`, `messageDeleted`, `labelAdded` and `labelRemoved`, then batched `messages.get(format=full)`.
  - Upserts are keyed on `(mailboxId, gmailMessageId)`, so replays are harmless.
  - `historyId` only advances after the page is committed.
- **Gaps:** `history.list` returns **404** when `startHistoryId` is too old (history is typically kept about a week, sometimes less). The worker then runs a **full resync** over the backfill window and reconciles.
- **Backfill:** `messages.list(q: newer_than:<N>d)`, resumable via `backfillPageToken`.
- **Timers:**
  - The watch is renewed **daily**. Gmail requires at least every 7 days.
  - Each mailbox is polled with `history.list` every 5 minutes as a safety net.
  - Watched mailboxes get at most 1 notification per second.
- **`format=full` rather than `raw`:** `raw` downloads every attachment's bytes with the message, while `full` only includes attachment ids, which enables lazy fetching (D-027).
- **Google Groups:** A group address can't be read through the Gmail API. The IT address must be a real user mailbox, or the group must deliver to a member user mailbox that we connect (documented in `docs/ARCHITECTURE.md` §9).

### D-036: Transactional email through a provider abstraction

_Accepted 2026-09-29: the Google Workspace SMTP relay (`smtp-relay.gmail.com:587`, STARTTLS, SMTP AUTH as a dedicated sender user, with the server's IP registered in the relay settings), sending from `noreply@vtk.be` as "Dopl". Change it in `.env` if needed._
**Decision:** The `Mailer` interface has an SMTP implementation via Nodemailer. All sends go through the `outbound_emails` outbox and a worker job with retries. Which provider sits behind it is your call (Q-3). Options are the Google Workspace SMTP relay, Brevo (a Brevo connector is visible in this environment), or another SMTP server.
**Why not the Gmail API for these?** Confirmation emails, magic links and digests shouldn't depend on the shared IT mailbox's sending quota or show up in its "Sent" folder.

### D-037: Object storage via the S3 API; Garage for production — _Proposed_

**Decision:** The `BlobStore` interface has two drivers:

- `s3`, using `@aws-sdk/client-s3` with `forcePathStyle` for self-hosted endpoints, presigned PUT/GET and 5-minute URLs
- `local`, for development and tests, storing files on disk and serving them through a signed route handler

Buckets are never public; downloads always go through a policy check and a signed redirect. Upload limits are enforced by the presign policy (`content-length-range`) and checked again on confirm.
**Production backend:** Garage is my suggestion. It's lightweight and built for self-hosting, and it runs as a separate service. Its AGPL licence covers only that service. MinIO's community edition changed its distribution and feature set in 2025, so check its status before choosing it. Any S3-compatible store works (Q-5).

## Decisions added after Phase 0 review (2026-09-29)

### D-049: Stay on Prisma 7.x: Prisma 8 is still a release candidate

**Context:** You said to use Prisma 8 "if it's already available". As of 2026-09-29 it isn't released:

- `prisma@latest` on npm points at `8.0.0-rc.17`, but `@prisma/client@latest` is still `7.10.0`.
- Prisma's release-status page says 8 is a release candidate, with general availability expected in October 2026.

Prisma 8 is also a rewrite:

- It ships a new client package (`@prisma/orm-postgres`) and removes `@db.*` attributes.
- It renames `take`/`skip` to `limit`/`offset`.
- It doesn't have `$extends`, JSON filtering, atomic `increment`, most nested writes, transaction isolation levels or `P2002`-style unique-violation errors yet.

**Decision:** Stay on `prisma@~7.10` and `@prisma/client@~7.10`.
**Why:**

- Better Auth's Prisma adapter supports `prisma ^5 || ^6 || ^7` only.
- We rely on nested writes, increments and unique-violation handling (sequences, invites, idempotent submissions).
- Prisma 7 gets fixes and security updates for 18 months after 8 reaches GA.

**Follow-up:** Re-evaluate once Prisma 8 is GA _and_ Better Auth supports it. Keep Prisma-specific code inside `packages/db` and `server/data|services` so a migration stays contained.

### D-050: Invite-only accounts; Google, email + password, SSO and magic links

**Decision:**

- **No self-sign-up by any method.** An Owner or Admin invites an email address. That creates the `User` row, a `WorkspaceMember` (status INVITED, role Member or Guest) and a `WorkspaceInvite` token.
- The invite link (`/invite/<token>`) lets the invitee choose how to sign in:
  - **Google.** `disableSignUp: true`. The optional `GOOGLE_HOSTED_DOMAIN=vtk.be` only pre-selects the Workspace account.
  - **Email + password** (Better Auth `emailAndPassword`, `disableSignUp: true`). The invite link doubles as the "set password" link, so accepting it verifies the email address.
  - **SSO** (`@better-auth/sso`, OIDC or SAML). Providers are configured by an Admin in Settings → Authentication, or statically from env. It uses `disableImplicitSignUp: true`.
  - **Magic link** (`disableSignUp: true`). This is the default for guests and available to members.
- **Linking:** `account.accountLinking` is enabled with `trustedProviders: ["google", …ssoProviderIds]`. An invited user's first Google or SSO sign-in links to the pre-created user by _verified_ email.
- **2FA:** TOTP 2FA (Better Auth `twoFactor` plugin) is available to password users and **required for Owner and Admin accounts that use a password**, because the app is public (D-051).
- **Bootstrapping:** `pnpm dopl:bootstrap --email you@vtk.be` creates the workspace and the first Owner and prints a one-time invite link.
- Admins can disable individual sign-in methods per workspace.
- The SSO and 2FA tables are generated with the Better Auth CLI in Phase 1.4 and added to `schema.prisma` then. Their exact field names must match the plugins' schemas.

**Why:** You chose invite-only and asked for Better Auth logins and/or SSO. Pre-creating the user makes "invite-only" hold uniformly, because every method runs with sign-up disabled.
**Open:** Which SSO identity provider (Q-21)? Until then, generic OIDC is supported and covered by an e2e test against a local mock IdP.

### D-051: Public deployment at `dopl.vtk.be`, hardened for the open internet

**Decision:** The whole app is public behind Caddy at `https://dopl.vtk.be`. There's no VPN, so we add:

- **Transport:** HSTS (with `includeSubDomains` once confirmed), secure cookies (`useSecureCookies`), and `BETTER_AUTH_URL=https://dopl.vtk.be`.
- **Auth defences:**
  - strict rate limits on `/api/auth/*`: 5 password attempts per 15 min per account+IP, then exponential backoff
  - generic error messages, so no account enumeration
  - required 2FA for password-based admins (D-050)
  - session list with remote sign-out
  - audit entries for failed logins
- **Surface:**
  - `/dev/ui` and the e2e auth provider are compiled out of production builds
  - `/api/healthz` returns no version info
  - a `robots.txt` that disallows everything except `/f/*`
- **Headers:** CSP per D-029, `frame-ancestors` per form for `/f/*`, and `Referrer-Policy: strict-origin-when-cross-origin`.
- The Google OAuth redirect, SSO callbacks and the Workspace SMTP relay are configured for this hostname.

### D-052: Discord webhooks for updates, new tickets and new mail

**Decision:** Outgoing webhooks are configured in Settings → Integrations (`OutgoingWebhook`, kind `DISCORD`):

- **Scope:** events, projects and mailboxes. Some example event keys are `work_item.created`, `work_item.state_changed`, `work_item.completed`, `work_item.assigned`, `intake.submitted`, `intake.accepted`, `email_thread.created`, `email_message.received` and `agent.approval_requested`.
- **Delivery:** services enqueue domain events in the mutation's transaction, and the worker's `webhook.deliver` job renders a Discord **embed**:
  - title `INFRA-42 · Title` linking to Dopl
  - colour from the state group
  - fields for state, priority and assignee
  - username "Dopl" and the Dopl avatar
- **Coalescing:** updates to one entity within 60 s become a single message (`coalesceKey`), so a burst of edits doesn't spam the channel.
- **Safety:**
  - Every payload sends `allowed_mentions: { parse: [] }`, so untrusted text such as an email subject containing `@everyone` can never ping anyone.
  - Content is truncated to Discord's limits. `includeContent` is **off** by default: titles and links only, so personal data from contacts doesn't leave Dopl unless an admin opts in.
  - The webhook URL is encrypted at rest (it contains a token).
- **Reliability:**
  - Discord's `429` responses and their `retry_after` are respected.
  - Failures retry with backoff. After 10 consecutive failures the webhook is auto-disabled and admins get an Inbox notification.
  - The delivery log is kept 30 days, with "Send test message" and "Redeliver" buttons.
- **Approvals are never actionable from Discord.** The message links back to Dopl, where approval requires sign-in.

**Phasing:** the framework plus work-item and intake events come in Phase 3, mail events in Phase 7, and agent approval events in Phase 8.

### D-053: "Hide done" is a first-class display option, on by default

**Context:** This was one of your three Plane pain points: done items can't be filtered out of a project's item overview.
**Decision:** `DisplayOptions.completed: "hide" | "recent" | "show"`. The default is **"hide"** for project and workspace views.

- `"recent"` shows items completed or cancelled in the last 14 days.
- The toolbar always shows a chip, "Done hidden · 23", that toggles it in one click (shortcut `⇧H`).
- On a board grouped by state, the Done and Cancelled columns stay visible but **collapsed**, showing their counts.
- The setting is saved per view, and per user for unsaved views.

It's a display option rather than a filter rule, so it composes with any filter. Setting it to "show" can still be combined with an explicit `stateGroup` filter.
**Acceptance (Phase 1.7):** opening any project list hides done items by default. One click shows them, and the choice survives a reload.

## Decisions made while building Phase 1 (2026-09-29)

### D-054: Reads go through internal JSON routes; writes go through server actions

**Context:** TanStack Query needs a fetcher for refetches, pagination and cache invalidation. Server actions are serialized per client and are POST-only, which makes them a poor fit for parallel reads.
**Decision:** Client reads call internal route handlers under `/api/v1/[ws]/…` (`projects/[projectId]/items`, `projects/[projectId]/meta`, `items/[ref]`, `search/items`, `files/[id]`). Every handler resolves the session and workspace through `requireWorkspaceCtx` and runs the same policy checks as the services. Writes stay in server actions (`src/server/actions/*`) that return the `ActionResult` shape. The first page is still rendered on the server where it matters (D-009).
These routes are **internal**: they have no stability promise. The public REST API with tokens (Phase 8/MCP) will be a separate, versioned surface.

### D-055: No e2e auth backdoor; tests sign in with the real password flow (supersedes part of D-046)

**Context:** D-046 planned a dev-only credential provider behind `DOPL_E2E=1`. On a public deployment (D-051), any bypass that could be switched on by an environment variable is a risk.
**Decision:** There is no e2e provider. Playwright's global setup signs in as a seeded member (`bram@dopl.test`) with the normal email + password form and saves the storage state. The seed, which refuses to run when `NODE_ENV=production`, gives the seeded people a dev password. The roadmap's "production build fails if the e2e provider is enabled" check is therefore unnecessary.

### D-056: e2e tests run in their own sandbox project

**Context:** e2e tests that edit, drag and delete seeded items made the seed data drift, which broke screenshots and made test order matter.
**Decision:** The global setup creates an **E2E sandbox** project (identifier `E2E`) if it doesn't exist, and every mutating test works there with items it creates itself. `pnpm db:seed -- --reset` (dev only, refuses in production) deletes the seeded projects, including the sandbox, plus view preferences, and rebuilds them.

### D-057: pnpm 10, not pnpm 11+

**Context:** pnpm 12 is a Rust rewrite and still settling; our lockfile, `onlyBuiltDependencies` and catalogs are pnpm 10 features.
**Decision:** Pin `packageManager: pnpm@10.34.6` and set `manage-package-manager-versions=true` in `.npmrc`, so everyone uses the same version. Revisit once pnpm 12 is stable.

### D-058: ESLint 10 for packages, ESLint 9 for `apps/web`

**Context:** `eslint-plugin-react` (pulled in by `eslint-config-next`) crashes on ESLint 10.
**Decision:** The root flat config (packages and worker) uses ESLint 10 with `typescript-eslint` strict type-checked rules. `apps/web` keeps its own `eslint.config.mjs` on ESLint 9 with `eslint-config-next`. Move web to ESLint 10 once the React plugin supports it. Seeds, tests and `testing/` helpers may use non-null assertions.

### D-059: Plain template functions for email for now (amends D-045)

**Context:** Phase 1 only sends four transactional emails (invite, magic link, password reset, email verification).
**Decision:** Templates are plain TypeScript functions in `packages/shared/src/emails/templates.ts` that return `{ subject, html, text }` with escaped interpolation and one shared layout. The web app enqueues an `email.send` job inside the mutation transaction; the worker renders and sends it over SMTP (Mailpit in dev, the Workspace relay in production). ### D-060: Attachments: local disk by default, S3-compatible optional

**Context:** D-032 planned Garage in the dev compose file. For a single-server deployment a mounted volume is simpler.
**Decision:** `src/server/storage` has a `BlobStore` interface with a `local` driver (default; `STORAGE_LOCAL_DIR`, `.data/uploads`) and an `s3` driver (`STORAGE_DRIVER=s3` + the usual S3 variables, works with Garage, MinIO or R2). Uploads go through `/api/v1/[ws]/items/[ref]/attachments`, which checks the item policy and the size limit; downloads go through `/api/v1/[ws]/files/[id]`, which checks the item's policy on every request (and redirects to a short-lived signed URL on S3), so files are never publicly addressable.

### D-061: Operational notes for AI-assisted development

- **Prisma refuses destructive commands (`migrate reset`) when it detects an AI agent** unless the user types an explicit consent phrase. Agents must not work around this. Tests use `migrate deploy` on `DATABASE_URL_TEST` and isolate data per test with their own workspaces.
- **Building the Docker images locally crashed the OrbStack daemon twice** during `next build`. Images are built in CI (the `images` job pushes to GHCR); locally, use `pnpm build` for a smoke build.
- After `pnpm add` in `apps/web`, Turbopack can serve stale modules. Restart `pnpm dev` and delete `apps/web/.next/dev`.

## Decisions made while building Phase 2 (2026-09-29)

### D-062: How item lists load, and how big they may get

**Context:** The performance pass (`pnpm perf`, 50,000 items in 10 projects) showed that planning and indexes are fine (every access path is an index scan, 0.3–26 ms server time). The cost is in returning rows: about 12 µs per row for transfer and parsing, whether through Prisma or `pg` directly.
**Decision:**

- Lists load in two steps. Prisma applies the compiled filter and returns ids only. Then one SQL query fetches those rows, with assignees and labels aggregated in Postgres (CTEs, not a subquery per row).
- Caps per response: **10,000 rows** for a project list and **2,000** across projects, where the most recently updated rows win. A capped list shows a notice asking for a narrower filter.
- Measured p50: filtered views 7–22 ms; workspace views about 35 ms; a 3.3k-row project list about 38 ms; the unfiltered 5k-row list about 66 ms. p95 is noisy on a shared dev machine (GC pauses), so the harness asserts p50 against the budget and reports p95. The budget is 50 ms for filtered views and lists up to 2,000 rows, and linear (15 ms + 15 µs per row) above that.

**Revisit when** a single project passes about 5,000 open items. Options: denormalized `assigneeIds`/`labelIds` arrays on `work_items`, server-side grouping with per-group windows, or streaming rows.

### D-063: Realtime transport as built (amends ARCHITECTURE §4)

- One `LISTEN dopl_realtime` connection per web process, on a dedicated `pg` client rather than the Prisma pool. It reads each `realtime_events` row once and fans it out to that workspace's SSE streams (`/api/v1/[ws]/realtime`).
- Each connection keeps a permission snapshot: accessible project ids, plus a cached item-to-project lookup for `workItem:` topics. `user:` topics go only to that user. The snapshot is refreshed on `project.*`, `member.*` and `invite.*` events.
- `Last-Event-ID` replays up to 500 missed events; beyond that the server sends `resync` and the client refetches everything. Keepalive `: ping` every 20 s; the client reconnects with backoff.
- The client batches events for 150 ms, invalidates the matching queries, and refreshes server-rendered pages (Home, sidebar, view lists) with `router.refresh()`. **It waits while local mutations are in flight**: otherwise a refetch can land between an optimistic update and its write and put the old value back (found by the e2e run).
- **Not built yet:** the BroadcastChannel leader tab (one stream per browser). Each tab opens its own stream, which is fine at our size over HTTP/2. The "flash the changed field" treatment (DESIGN_SYSTEM §7.2) is also still to do.

### D-064: Filter semantics

- The AST lives in `@dopl/shared/schemas/filters`. The server compiler is `apps/web/src/server/queries/filters.ts`, with a database test for every field × operator (78 pairs).
- "is none of" on a nullable field (type, parent, created by) **keeps items where the field is empty**. Otherwise excluding one type would silently drop untyped items.
- Date rules compare calendar days in the **workspace time zone**; timestamp rules convert those days to instants in the same zone. Dynamic values: today, yesterday, tomorrow, start and end of this week and month, and within the last or next N days, weeks or months.
- Quick filters are ordinary top-level rules of an AND root, so they combine with anything and show up as chips.
- An unsaved view keeps its filters per user and scope (`ViewPreference`) and mirrors them into `?f=` so links can be shared. On load, a URL filter wins over the saved one.
- In the builder, the parent field only offers "is empty / is set". `in` on parent ids stays available in the AST for the API and the agent.

### D-065: Saved views

- Private views are the owner's. Shared views are visible to everyone who can see the project (or the workspace, for cross-project views).
- Any non-guest human can edit a shared view unless it's **locked**. Only the owner or an admin can lock, change visibility, or delete it (`canView` in the policy module).
- Opening a saved view seeds the page with its settings. Changes are **not** auto-saved: the filter bar offers Reset, Save (if you may edit) and Save as new. Unsaved project and workspace pages keep auto-saving their last-used settings.
- Favourites (the `favorites` table) pin views to the sidebar and disappear with the view.

### D-066: Cross-project (workspace) views

- Non-guests only; a guest's access is per project and may exclude browsing.
- Grouping by state becomes grouping by **state group**, because each project has its own states; you can also group by project. Manual order falls back to priority. The state and label pickers narrow to the row's own project, and a board drop into a state group picks that project's first state in the group.
- Creating items from a workspace view isn't offered yet: the create dialog needs a project picker.

### D-067: Table, calendar and timeline

- **Table:** TanStack Table 9 owns column state only (sizing, resizing, order, visibility); we render the virtualized rows ourselves as memoized components, so editing a cell re-renders one row. Column order and widths are saved in `DisplayOptions.table.columns`; visibility follows the display properties. The title column is pinned.
- **Calendar:** dragging changes only the date shown (due or start). If the start would end up after the due date, the server rejects it and the change rolls back. Keyboard: Shift+arrows move by a day or a week, and focus stays on the item.
- **Timeline:** a drag or resize sends start and due together in one update. A dependency is drawn red when the blocker ends on or after the day the blocked item starts.

### D-068: Keyboard registry and the command palette

- Every shortcut is defined in `apps/web/src/lib/shortcuts/registry.ts` with a scope. Handlers resolve key events through it, the `?` overlay is generated from it, and a unit test checks for conflicts and missing labels. Physical keys are used for punctuation with ⌘ (⌘⇧, reports `<`).
- The palette acts on "the current item": the one open in peek or on its page, else the focused row. Views publish it through a tiny external store (`features/palette/context.ts`). Item property changes from the palette are nested pages.
- "Recent" comes from `recent_visits`, recorded by a server action when an item, project or view opens. Access is checked when recents are read, not when they're written.

### D-069: Bulk operations

- Each bulk operation is one transaction and one activity batch. **Undo** sends each item's previous values (taken from the client cache) back through `patchManyWorkItems`. Archive and delete undo by reversing the flag for the same ids.
- **Move to project** gives items new numbers in the target project and maps the state to the target's state in the same group (the default one if possible). Project labels map by name; workspace labels stay. Parent links that would cross projects are cut, with counters fixed. **Old identifiers don't redirect yet** (see Q-23).

### D-070: Keeping the e2e suite deterministic

- `<html data-saving>` is present while mutations are in flight. Tests wait for it to disappear instead of `networkidle`, which the always-open realtime stream makes meaningless.
- The Playwright setup empties the E2E sandbox (select all, delete) before the run.
- Next keeps the previous route mounted (hidden) for instant back navigation, so a test id can match twice. Specs act on `filter({ visible: true })`.
